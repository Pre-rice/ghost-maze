# 鬼迷宫：当前状态、方案与决策依据

更新：2026-10-11。范围：游戏本体与 AI。状态：诊断与方案，尚未实施整改。

**现有基础可以沿用。应该统一正式游戏规则，并以操作序列贯通历史、存档点、AI 路线和回放。** 当前尚未全部共用一份实现；分享失败已有明确复现，不能归因于地图不可解。

本报告保留原八项范围：内核独立、历史统一、死亡循环、游戏内回放、随机设置边界、地图网址、分享机制、AI 一致性与真人数据。下表先给出使用层面的结论，分享格式在第 7 节展开。

| 事项 | 当前状态 | 本次方案 |
|---|---|---|
| 规则引擎 | 本体使用正式规则；AI 参考求解使用固定版本，快速求解另有实现；回放使用页面提供的版本 | 游玩、参考验证与回放使用同一规则基线；快模拟只作加速，路线仍由正式规则核验 |
| 每步历史 | 本体逐步保存局面，未准确记录原始操作 | 操作序列作为路线记录；局面仅作当前状态和临时加速缓存，不写入回放码 |
| 存档点 | 页面内的步号标记，刷新即丢；恢复边界有缺口 | 保留本局存档点，供撤回和回溯；不增加本机持久存档 |
| 死亡 | 两模式入口不同；死亡循环复活后仍保留旧历史与存档点 | 两模式均提供回到上一存档点、完全重来；死亡循环另保留原复活玩法 |
| 死亡循环 | 复活保留已探索区域；循环次数进入通关文案 | 保留逐次揭图，提供全图选项；只记录当前这一命，循环次数仅供参考，不写入回放，通关无需显示 |
| 回放 | AI 有独立回放页，固定约 800 毫秒一步；本体没有完整入口 | 同一游戏页面播放、暂停、调速、选步，默认全图；可以加载某一步继续玩 |
| 回放网址 | 现有 AI 链接依赖服务器上的录制编号 | 地图网址追加回放码：`?map=地图码&replay=操作码`；不重复把地图塞入回放码 |
| 视野 | 局面快照记录已探索区域，复活继承 | 回放不记录探索历史；接管只加载物理局面，视野按当前游玩状态处理 |
| 设置 | 游戏界面仍能改玩法；直接试玩与网址打开可能使用不同初始资源 | 已有地图的结构、玩法和初始资源只能在编辑器修改；主题、方向键、全图等简单设置直接展示 |
| 地图分享 | v3 编码；存在生成成功却解码失败或内容改变的情况 | 分享必须可往返还原；是否升级格式由用户决定，不先改协议 |
| AI 路线 | 成功证书、真人保留路线已保存；搜索分支并非全部落盘；模型训练尚未启动 | 已保存操作可直接转换回放；真人、求解器与测试路线保留来源和版本 |
| 编辑器页面 | 目前与游玩在同一页面切换 | 明确独立编辑入口；是否拆为独立页面仍待用户决定 |

## 1. 内核：现在是否共用同一个游戏规则引擎？

**尚未全部共用同一份实现，但应该统一。**

| 环节 | 现在怎么执行规则 | 结论 |
|---|---|---|
| 游戏本体 | 调用本体的游戏规则 | 本体的正式行为来源 |
| AI 参考求解、路线核验与示范数据制备 | 调用固定游戏版本的规则 | 直接复用，但不一定等于本体当前工作区版本 |
| AI 快速求解 | 使用另写的加速模拟器，成功路线再交给参考规则重放 | 规则目标一致，迁移实现不同 |
| 现有 AI 回放 | 调用回放服务提供的游戏页面版本 | 默认可为固定版本，也可配置成本体；不能凭“都是 GameLogic”认定版本一致 |

AI 当前固定基线为 `9825376f2cf93f844146c83214f680425c22498b`，地图格式为 v3。本体已有地图检查、虚空墙规范化等变化，未自动同步到这个基线。

本轮把一条既有 70 动作路线放在共同规范化后的地图上重放，两个版本的 71 个物理与探索状态一致。原始旧录制的全量终局与当前版本仍有 87 处墙类型差别，均为虚空实墙被规范化为空；玩家、资源和鬼位相同。**这证明该例的差别来源，并不证明两个版本对所有地图都完全一致。**

**建议：** 正式游玩、回放、AI 参考验证共用同一规则基线、同一开局约定和地图要求。快速模拟器可以保留，继续逐状态对照正式规则，并让输出路线通过正式引擎确认。强制搜索中的每一步都用较慢的完整引擎，会损失速度；只让快实现自行证明正确，又会留下分歧风险。

以后换前端、加入不同界面或线性关卡，沿用相同规则即可。界面负责展示、输入和关卡组织；播放速度不改变鬼的追捕、体力消耗和胜负顺序。

## 2. 历史：每步只保存操作，是否可行？

**可行，适合作为正式路线记录。** 在地图、初始玩法和规则版本固定后，上下左右及空格楼梯足以重新计算物理局面。按钮由对应方向操作触发，即使玩家没移位，也必须记为有效一步。

本轮未发现影响物理结果的随机数；真实时间用于画面轨迹。两次重放既有路线，排除动画时间后，物理与探索结果逐步相同。因此不需要为分享每一步的玩家、鬼、门和物品局面。

### 记录怎么使用

- 当前局仍然持有一个可游玩的局面，历史以实际生效的操作记录。
- 撞墙等没有改变状态的输入不记入路线；不记录思考停顿或原始按键时长。
- 存档点只是当前路线中的步号，本局使用即可，不写入本机持久存储。
- 撤回、回到存档点、回放选步都通过同一套规则恢复目标物理局面。
- 返回早先一步后继续走，保留前缀，再形成新分支；新分支不会混入原来的后续操作。
- 已探索区域属于当前游玩会话，不作为回放记录。回放接管不还原录制者的探索历史。

### 为什么仍建议临时缓存局面

操作记录省空间，但跳到第 N 步需要执行前 N 个操作。若每次拖动都从起点重新计算，长路线可能等待明显。

| 本轮恢复测量 | 中位耗时 |
|---|---|
| 既有短图，70 个动作 | 约 21 毫秒 |
| 20×20 单层，1000 个有效动作 | 约 1.4 秒 |
| 20×20 十层，100 个有效动作 | 约 1.6 秒 |

这是本机 Node 的定向测量，后两项为无鬼的恢复压力样例；不是浏览器拖动体验的保证，也不涵盖所有复杂图。

**建议采用“操作是记录，局面是临时缓存”。** 缓存可以丢弃后重新生成，无需每步都永久保存，也不进入分享码。这样保留短码，又不会要求玩家每次切步都等从头计算。

之前推荐每步完整局面，是为了直接恢复、顺畅拖动；当时尚未验证只存操作的恢复成本。现在明确无本机存档、分享需要短码，并验证了确定性与长路线成本，所以调整为操作记录加临时缓存。省空间和即时恢复分别解决，理由并非“用户提出什么就改成什么”。

## 3. 死亡、复活、存档点与完全重来

按用户已确认的行为：

| 操作 | 物理局面 | 历史和存档点 | 探索与循环 |
|---|---|---|---|
| 死亡后回到上一存档点 | 恢复该点的玩家、鬼、物品、门、生命或体力 | 使用本命当前路线的存档点；恢复后能继续走新分支 | 按当前游玩视野处理 |
| 死亡循环的原复活 | 地图和资源回到初始物理状态 | 新一命开始，上一命历史和存档点不继续作为活动记录 | 保留已揭区域；循环次数仅供参考 |
| 完全重来 | 同一地图按作者设定重新开局 | 清除本局路线和全部存档点 | 清除探索进度和循环计数 |

两种玩法都提供“回到上一个存档点”，没有存档点时清楚显示不可用。探索模式的原碰撞、扣生命规则不因此改写；到其失败条件时提供上述选择。

“重来”恢复的是这张地图的初始状态，不重新随机生成另一张图。初始生命、体力和玩法也恢复作者设定。

死亡循环保留逐次揭图玩法，另提供全图查看。只需记录当前、最终这一命；回放不包含之前各命、复活动作、循环次数或继承的探索区域。死亡画面仍可查看刚结束的本命过程，直到复活或重来开始新记录。

当前旧历史与存档点会跨复活残留，撤回和回溯的限制不一致；这是需要整改的实际缺口。旧录制文件继续保留，不因新的活动历史边界直接删除。

## 4. 回放：分享、调速、选步和接管

**回放入口使用同一游戏页面，并依赖地图：**

`https://ghostmaze.novic.cc/?map=地图码&replay=操作码`

先打开地图及其作者设定，再读回放操作并进入观看。只有地图码时从头游玩；没有地图的回放码不能独立打开。回放码不重复包含整张地图，但需要识别所绑定的地图与规则，避免在另一张图或另一套规则上误放。

应有的使用能力：

- 播放、暂停、前后切步、输入或拖动到指定步。
- 可选速度，例如 0.5×、1×、2×、4×；速度仅影响播放节奏。
- 默认看全图，不记录录制者的视野、循环次数和思考用时。
- 选择某一步后，点击“从这一步继续玩”，恢复该步的玩家、鬼、门、物品、资源与胜负状态。
- 接管只加载物理局面；视野按当前游玩状态处理，不导入录制者已探索区域。
- 接管后保留该步之前的操作前缀，后续实际操作形成自己的新路线。外部回放不附带录制者的存档点，接管后可以自行创建。
- 观看与接管是两个明确动作。单纯观看、拖动或退出回放，不自动替换正在玩的局。

死亡步或胜利步也应恢复对应状态；不能为了“继续”擅自把死亡或胜利抹掉。死亡步仍使用正常的回存档、复活或重来入口。

现有 AI 回放已经能播放、暂停、拖动和全图观看，但速度固定，处在独立页面，以服务器录制编号读取文件。**它并不等于上述同页、可分享操作码、可接管的功能已经完成。**

### 回放码会有多短

五种操作直接打包，每步 3 bit：1000 步约 375 字节，转成网址安全文字约 500 字符，尚未计格式头与地图码。重复较多时压缩还可能缩短，但不能保证。

实测既有 70 动作路线：操作打包为 27 字节、36 字符；再压缩为 29 字节、39 字符，反而略长。因此短路线不应为了“压缩”强制变长，可以保留更短的表示。

这些是**动作部分**的大小，不是完整网址长度。地图、动作数、格式版本和绑定信息另算；无需附每步局面、初始探索位图或循环记录。

## 5. 随机生成、已有地图和设置边界

**已有地图只能进编辑器修改结构、玩法和初始资源。** 游玩时固定这些内容，不再允许切换玩法后重开成另一套题。

| 内容 | 放在哪里 | 生效边界 |
|---|---|---|
| 随机尺寸等生成选项 | 随机生成按钮内部 | 只影响下一张新生成的地图 |
| 墙、鬼、钥匙、机关、活动格、起终点、层与楼梯 | 编辑器 | 编辑后的地图成为新的地图版本 |
| 探索／死亡循环、初始生命和体力 | 编辑器，随地图保存 | 直接试玩、分享打开、重来都应一致 |
| 主题、方向键面板、全图查看等简单显示或操作设置 | 游玩界面直接展示 | 不改作者地图和初始玩法 |

目前直接编辑器试玩与分享后打开的开局参数仍可能不同。这必须先统一，否则回放和 AI 即使使用相同动作，也可能在不同体力条件下得到不同结果。

全图可选是用户已确认的能力。真人路线若用于分析迷雾体验，仍不能仅凭一条操作路线推断当时是否使用全图；新方案不为回放增加视野历史。

这次整理不替换随机生成算法、不改变鬼的行为，也不恢复已暂停的谜题设计或训练。

## 6. 地图网址与编辑器是否独立成页

地图网址 `?map=…` 已存在，保存的是原始地图和初始玩法，从头开局；不保存当前进度。

入口建议仍为：编辑完成后生成、复制完整地图网址，游玩中可复制原地图网址；不要求玩家单独管理裸分享码。取消裸码界面不等于取消地图编码。

### 编辑器页面的两个选择

| 方案 | 主要收益 | 需要处理的代价 |
|---|---|---|
| 保持同页编辑模式 | 编辑、试玩、返回较直接，保留未完成草稿容易 | 必须明确区分编辑与游玩控件，避免游玩中出现可改地图的入口 |
| 独立编辑页面或网址 | 游玩界面职责清楚，可以直接打开编辑入口；符合只在编辑器改地图的边界 | 试玩后返回必须保留草稿，不能切页就丢失编辑内容；入口与返回流程增加 |

**我的倾向是独立编辑入口和界面，可进一步独立成页，但拆页不是锁定游玩地图的前提。** 如果优先这轮改动小、草稿切换顺畅，同页模式也能满足要求；如果优先长期清楚的游玩／创作入口，独立页更合适。用户尚在考虑，因此不提前替用户决定。

无论选择哪种，编辑器都共用地图格式、校验和试玩引擎。拆页面不需要复制规则。未完成草稿的返回保留属于编辑体验，不因此引入本机持久存档。

## 7. 现有分享码机制：保存了什么，怎么变成网址？

**链路是：原始地图和初始玩法 → 固定格式的二进制数据 → 无损压缩 → 网址安全文字 → `?map=…`。**

它直接把地图装进网址，不是向服务器申请一个地图编号，也不是加密。页面能读取该格式时，就可以从网址还原地图，无需发送者电脑上的文件。

### 7.1 保存内容和不保存内容

保存：地图尺寸、玩法、初始生命／体力、常规或自由编辑模式、活动格、原始墙和门参数、鬼与钥匙初位、按钮、起终点、楼层和配对楼梯。

不保存：当前玩家位置、当前鬼位、已拿走的物品、游玩后门态、当前生命／体力、已探索区域、动作历史、存档点、主题和方向键设置。

因此通关后分享地图，别人仍从头开始。分享这一段游玩过程需要额外的回放码。

### 7.2 头部和普通数据

当前格式为 v3。版本头表示的是**地图编码格式版本**，并不记录某次游戏规则更新的版本。

| 数据 | 当前表达方式 | 作用与限制 |
|---|---|---|
| 格式版本 | 1 字节，目前为 3 | 解码器据此选择格式；现在不读 v1／v2 |
| 宽、高 | 各 1 字节 | 编码器接受 1–64；当前编辑器支持 8–20 |
| 模式 | 1 字节中的三个开关 | 探索／死亡循环、常规／自由、多层与否 |
| 初始生命 | 1 字节 | 可表达 0–255，实际玩法要求有效正值 |
| 初始体力 | 2 字节 | 可表达 0–65535 |
| 终点坐标 | x、y 各 1 字节 | 两个 255 表示没有终点 |
| 自由模式起点 | x、y 各 1 字节 | 常规起点由固定规则推导，不单独保存任意起点 |
| 自由模式活动格 | 每格 1 bit | 按行排列，20×20 一层为 50 字节；末尾不足字节补零 |
| 鬼与钥匙列表 | 数量 1 字节，每个位置 2 字节 | 每类数量最多表达 255；保留排列顺序 |
| 按钮列表 | 数量 1 字节，每项位置、朝向、字母共 4 字节 | 数量最多表达 255；朝向为上 0、下 1、左 2、右 3 |

头部、实体和参数以字节为单位，墙类型和活动格以位为单位。这样避开 JSON 字段名和重复文字，通常比直接把地图 JSON 放进网址短。

### 7.3 墙体如何打包

横墙先逐行记录，再记录竖墙；所有墙类型连续写入，整层墙流结束时才补齐字节，不是每一行补齐。

| 类型 | 类型所占位 | 额外参数 |
|---|---|---|
| 空 | `0` | 无 |
| 实心墙 | `10` | 无 |
| 普通门 | `110` | 无 |
| 数字门 | `1110` | 钥匙要求 1 字节 |
| 单向门 | `11110` | 朝向 1 字节 |
| 玻璃 | `111110` | 无 |
| 字母门 | `1111110` | 字母 1 字节、初始开关 1 字节 |

常见的空与实墙用更短的码，复杂类型稍长。读取连续的 1，直到遇到 0，就知道类型；再按地图尺寸知道必须读多少面墙，不依赖猜测。

门的额外参数没有夹在墙类型之间，而是在整层墙流之后单独排列。**这份参数队列前只有 1 字节的长度，因此每层参数总量最多 255 字节。**

具体限制是：数字门数量 + 单向门数量 + 2 × 字母门数量 ≤ 255。只含字母门时，127 扇需要 254 字节；128 扇需要 256，已经超过格式容量。其他类型的墙不消耗这个参数预算。

多层地图在第 0 层之后记录层数、全局楼梯和其余层。楼梯每项保存位置、所在层与上下方向。后续层各有活动格、起终点、实体、墙类型和参数队列；每层独立受上述参数上限限制。

第 0 层只编码一次，使用顶层地图信息。这要求顶层与内部的第 0 层必须一致；当前生成端没有完整拒绝冲突输入。

### 7.4 压缩、网址编码和解码

二进制地图使用 `deflateRaw` 无损压缩。当前页面使用项目内提供的 pako 2.1.0；生成时比较默认、最高级别和游程策略三种结果，取最短。

压缩后的字节再变成 Base64URL：普通 Base64 的 `+` 换成 `-`，`/` 换成 `_`，去掉末尾 `=`。这些替换让文字便于放入网址；Base64URL 本身会把字节展开成约 4/3 的字符数，不是第二次压缩。

打开时反向执行：读 `map` 参数 → 还原压缩字节 → 解压 → 查版本 → 读头部、实体、墙类型和门参数 → 读其余层 → 检查数据没有不足或多余，并检查按钮依附 → 建立地图、按初始玩法开局。

同一地图可以有不同但等价的压缩字符串；不能仅凭码文本不同就认定地图不同。压缩不改变格式的数字容量，也不能修复生成前已溢出的长度。

### 7.5 一个合法小图的可复核例子

诊断样例：8×8，自由编辑、探索模式；所有格活动，外围实墙、内部相通；起点 `(0,0)`、终点 `(7,7)`，生命 5、体力 100，无鬼、钥匙、按钮和额外楼层。这是用于说明格式的小样例，不是新谜题交付。

- 头部为 `03 08 08 02 05 00 64 07 07 00 00`，共 11 字节。
- 活动格 64 bit，共 8 字节；三个空实体列表共 3 字节。
- 144 面墙中 32 面实墙、112 面空墙，类型流 176 bit，共 22 字节。
- 无门参数，但参数长度仍占 1 字节；总计 45 字节。
- 使用页面随附的 pako 在 Node 中核验，压缩产出 37 字节，转为 50 字符。

分享码：`Y-bgYGJlSGFnZ2D4DwUMDAyrVjFAwKpVDQFcjA4arAwLRJgYAA`

对应网址：[8×8 格式样例](https://ghostmaze.novic.cc/?map=Y-bgYGJlSGFnZ2D4DwUMDAyrVjFAwKpVDQFcjA4arAwLRJgYAA)。本轮已做本地编码、解码、地图可玩检查，原图和解码图沿右 7、下 7 均在 14 步胜利；未把该结果当作公网部署验收。

### 7.6 为什么能生成，却打不开或打开后变了？

**已经复现的第一类是编码容量溢出，而生成端没有拒绝。**

| 本轮 20×20 样例 | 门参数长度 | 生成 | 重新打开 | 原图通关 |
|---|---|---|---|---|
| 127 个初始开的字母门 | 254 字节 | 成功，92 字符 | 成功 | 38 步胜利 |
| 128 个初始开的字母门 | 256 字节 | 成功，91 字符 | 失败，参数队列不足 | 38 步胜利 |

两个输入均通过现有编辑器游玩校验。256 写入一个字节后变为 0，读取端以为没有参数，遇到字母门就无法继续。**这是生成端的缺陷，不能说用户的地图不可解；更短的失败码也没有使用价值。**

第二类更隐蔽：超过数值容量后，分享仍能打开，但内容已经改变。本轮确认初始生命 256、初始体力 65536、数字门门槛 256 都能生成并解码，却分别还原为 0。当前编辑设置或输入没有相应完整上限保护。这类问题仅检查“能否解码”还不够，必须检查地图和有效玩法是否相同。

第三类是内部同一地图信息冲突。本轮构造顶层终点为 `(7,7)`、内部第 0 层终点为 `(7,0)` 的输入：直接游玩取 `(7,0)`，分享再打开取 `(7,7)`。这属于冲突输入诊断，不声称正常编辑器每次都会产出这种冲突；但 AI 和导入路径都必须有一致处理。

鬼、钥匙、按钮和楼梯的数量也用一个字节，静态检查同样缺少完整的超限拒绝；本轮没有逐类构造全部边界例。旧 v1／v2 的版本不支持是另一类已明确的限制，不与上述新生成的坏码混为一谈。

### 7.7 分享格式的决策选项

| 选择 | 能解决什么 | 留下的代价 |
|---|---|---|
| 保留 v3，完整限制并校验往返结果 | 不再生成坏码，现有 v3 格式不变 | 合法但机关密集的地图仍会被拒绝分享；需要公开限制 |
| 升级格式，扩大可表达范围，同时保留 v3 读取 | 可覆盖当前编辑器支持的复杂图和资源设置 | 需要更新本体与 AI，并验证旧 v3 链接；旧页面不能自动读取新格式 |

**我的建议是升级格式、保留 v3 读取。** 编辑器允许制作的地图应能可靠分享；仅在分享时告知 128 扇门超限，体验不完整。

升级时也不必机械地把参数长度从一字节改成两字节：已经知道每面墙的类型，就能算出其需要几字节参数，可以去掉这个冗余长度，仍保持确定的线性解码。列表数量与资源值再选可变长整数或明确更大上限。这是下一版格式的候选设计，尚未定稿或实施。

地图格式升级与新增回放格式是两个决定。回放本身可以基于现有正常 v3 地图工作，但不能修复坏地图码。以后升级只承诺保留当前有效 v3，不自动扩大到早已不支持的 v1／v2。

## 8. AI：是否每条路径都保存，生成回放是否简单？

**已经保存操作的路线，转换回放很直接；不能说所有训练路径都已保存。** 当前模型训练尚未启动，现有工作是地图设计搜索、求解验证和示范数据准备。

| 数据 | 当前是否有操作路线 | 如何用于回放 |
|---|---|---|
| 已保存的成功求解证书 | 有动作序列及地图、规则信息 | 打包既有动作，再用绑定的正式规则确认即可 |
| 真人保留分支录制 | 有，主要从相邻局面恢复动作；等价动作时保留歧义 | 可还原同一结果，但不能冒称每个原始按键都被准确监听 |
| 求解中的全部搜索分支 | 运行时保留回溯关系，不承诺全量永久保存；已展开局面可释放 | 不存在“每条分支都能随时从磁盘取回”的现成功能 |
| 设计搜索档案 | 记录地图编辑链、尝试和分析，成功分析可含证书 | 地图编辑路径不是玩家的上下左右路径，需要取其中求解结果 |
| 已制备的监督样本 | 由经核验路线产生，保留来源和规则；未开始训练 | 对应源路线可以回放，样本数量不等于新增完整游玩局数 |

求解命令当前主要把结果输出到终端，并不每次自动存成文件；明确写入的成功证书和录制才是现成资产。本轮现场确认真人目录有 14 个录制文件，并读取了独立 QA 的 70 动作路线；测试录制不因此成为真人数据。

现有 AI 录制限制单条最多 2000 个有效动作。新版回放格式与完整网址的长度上限需在浏览器中验收，不能把“1000 步动作部分约 500 字符”当成任意长度过程都能分享的保证。

旧录制中含死亡和复活时，可以取最后一次复活后的操作，从原地图初态重放最后这一命。不再需要前几命动作、探索位图或循环次数；旧文件继续原样保留。

**整体建议：** AI 直接输出正式动作日志，游戏在动作发生时准确记录，回放读取同一种路线表示。三者共享地图和规则绑定，不再靠局面差分猜新记录的动作。快速求解生成路线仍经正式引擎重放。

验证服务与试玩页面必须对齐版本；合法地图要求、作者初始玩法、分享往返也必须一致。全图求解证书证明操作能执行，不证明迷雾下玩家自然能发现；最短路线或无伤通关也不自动等于真人觉得精妙。

这些核查不需要 Langfuse 账户或集成。项目文件、路线和规则重放已经足够，不增加外部 AI 服务范围。

## 9. 哪些建议改变了，之前与现在的理由是什么？

| 事项 | 之前的考虑 | 现在的依据与调整 |
|---|---|---|
| 每步保存局面 | 恢复目标步可以直接取局面，避免拖动等待 | 已确认操作可重建物理结果，短码是明确目标；实测长路线重算较慢，因此用操作记录加临时缓存 |
| 本机持久存档 | 曾把“存档”扩大理解为刷新后继续，推荐新增保存进度 | 用户明确不需要；保留页面内存档点，移除本机保存范围 |
| 回放单独参数、自含地图 | 为打开回放准备一份完整包，但重复了已有地图入口 | 用户要求在地图基础上加载回放；采用 `?map=…&replay=…`，不在回放码重复地图 |
| 回放仅观看 | 观看时保护原局，边界简单 | 用户明确要求选步接管；保留观看隔离，加入主动加载该步继续玩的入口 |
| 保存这一命初始探索区域 | 为准确还原录制者视野，并支持继承探索的局面接管 | 用户明确回放默认全图、接管不还原历史视野；因此删去探索区域记录，五种操作足够记录本命过程 |
| 死亡恢复只讨论死亡循环 | 原缺口主要在跨复活历史，范围集中于循环模式 | 用户明确所有模式都有回存档、重来；扩展恢复入口，保留死亡循环揭图复活 |
| 玩家切换玩法 | 曾作为作者设定之外是否允许修改的待决项 | 用户明确只有编辑器能修改；该项已确定，不再反复询问 |
| 循环次数 | 原玩法把累计次数展示为通关成绩，录制也带该值 | 用户只需参考；不纳入回放和通关展示要求 |
| 编辑器独立页面 | 原先侧重整理现有同页模式，控制改动范围 | 编辑／游玩边界现在明确，独立入口的收益更大；是否物理拆页仍是用户未确定的决策 |

## 10. 实施顺序与仍待决定的两项

建议顺序：

1. 对齐本体、AI、回放的正式规则基线与地图要求，统一作者设定的开局；确定分享容量范围。
2. 建立实际操作日志，贯通撤回、存档点、两模式死亡恢复与本命边界；局面缓存只用于加速。
3. 接入同页回放、地图加回放网址、调速、选步和接管；统一视野处理与来源标识。
4. 整理随机按钮、简单设置和编辑入口；若选独立编辑页，补齐试玩返回保留草稿。
5. 用既有地图、AI 证书和真人路线完成跨入口及真实浏览器验收，再结束整改。

| 尚待决定 | 我的建议 | 影响 |
|---|---|---|
| 地图格式保留限制，还是升级覆盖编辑器合法地图 | 升级并保留 v3 读取 | 决定复杂图是否继续存在分享限制，以及本体／AI 的格式兼容工作 |
| 编辑器是否独立成页 | 倾向独立入口和界面；独立页更清楚，但必须保留试玩返回草稿 | 决定编辑与游玩入口、返回流程及这轮 UI 范围 |

不做本机存档、回放调速与接管、全图默认、保留揭图复活、只记录本命、玩法仅在编辑器修改，已经按用户要求纳入。以操作作为历史记录是本报告基于上述验证给出的建议；这些方向不等于已经批准实施。

## 11. 怎样验收，当前哪些已证实？

完成标准：

- 同一张图直接试玩、网址打开、重来、AI 核验和回放，地图与初始玩法一致。
- 实际方向与楼梯操作能逐步重建玩家、鬼、物品、门和资源；按钮原地动作不漏记；缓存删除后仍能重建。
- 两模式死亡均能回到本命最近存档点；新一命不能恢复旧命存档；完全重来清除本局路线、存档与探索。
- 死亡循环复活保留揭图玩法，循环次数不进入回放；全图选项可用。
- 地图加回放网址可在没有录制服务器文件的环境中打开；调速、暂停、选步、接管可用；视野按当前游玩状态处理。
- 回放绑定地图与规则，错配或版本不支持时清楚失败，不能默默播放成另一局。
- 游玩固定已有地图与玩法；简单设置可用；随机设置只影响新图；独立编辑页若采用，试玩返回不丢草稿。
- 分享成功必须还原同一有效地图与玩法；容量边界、旧 v3、多层、按钮依附和内部数据冲突得到验证。
- AI 与游戏规则逐状态核验；真人、证书和 QA 保留来源，旧资产不覆盖、不删除。

本轮已证实：小图分享往返；127／128 字母门容量边界；生命、体力和数字门门槛截断；第 0 层冲突；既有 70 动作路线在共同规范化地图上的 71 状态一致；操作码体积与不同规模的重建成本；既有录制与搜索输出的保存范围。

**上述是诊断证据，不是整改已经完成。** 本轮仅更新本报告；未改游戏实现、界面、协议、规则锁或数据，未启动模型训练、生成新谜题、提交或推送。尚待用户决定两项范围并批准实施，再进行完整浏览器使用验收。
